# Fine-grained overlap for blockscaled FP8 MoE

**Analysis date:** 16 November 2026.
**Status:** Research and source inspection only. The owner selected option C: fine-grained kernel-level overlap among token dispatch, expert GEMMs, and token combine. No implementation has been accepted, and no local candidate parity test, GPU test, or performance measurement has been run.

## Decision

The selected direction is a fused MoE backend with overlap at expert or tile granularity: dispatch publishes ready input, a GEMM consumes it while other input is still arriving, and completed output feeds combine while other GEMMs continue. This is a substantial backend research and integration effort, not an adapter around the current public DeepGEMM calls.

The owner explicitly rejected both asynchronous-combine/shared-expert-only overlap and coarse token-chunk pipelines. Neither has an accepted implementation path, benchmark, or follow-up recommendation here. An earlier screening statement that shared-expert asynchronous combine overlap was already active was incorrect for the active HybridEP path: its combine wrapper joins the whole call, while the base dispatcher's `sync_combine()` is a no-op unless overridden ([HybridEP combine](../../gift/torchtitan/distributed/deepep/hybridep.py#L512), [dispatcher contract](../../gift/torchtitan/models/common/moe/dispatch/base.py#L157)). This source correction does not change the owner's choice of C.

The existing FP8 numerical recipe can remain the target contract. The unchanged public DeepGEMM calls cannot provide fine-grained producer/consumer readiness or publish partial expert outputs. A viable implementation therefore needs either to extend DeepGEMM's scheduler/mainloop/epilogue with explicit readiness, publication, and communication coordination, or to port the existing blockscaled FP8 arithmetic into a fused COMET/FlashComm-style GEMM. Rewriting the GEMM from scratch is not a requirement. No donor is a drop-in backend for the current training path.

## Local workload and numerical contract

The task checkout's source-inspection HEAD was `6c6cd9c0e41a0a5d3d00e1e252b3c120052d3507`. The V2 execution trace was produced from `3b6b8928ec4b15a529d07ee99e672f2fc75ef73a` with dirty-snapshot digest `ac22aae7ced85f3970b89e420010d87076b1ed0fa58b162b3aa245215aae35b7`. Earlier comparisons found no diffs in the relevant MoE, DeepGEMM, and activation-checkpointing files against the base and preserved `21c1891d` snapshot. Those are file-level comparisons, not proof of full dirty-tree or external-package identity. The trace and limits are retained in the [candidate screening receipt](../../runs/v2-prefetch-baseline/v2-candidate-screening-perfetto.json); the broader [V2 report](../../runs/v2-prefetch-baseline/report.md#L379) records environment metadata.

The capture's crop is one node with 8 H100 80 GB GPUs and NVLink: EP 8, dense FSDP 8, expert FSDP 1, TP/PP/CP 1; model width 4096, 128 experts, top-8 routing, expert width 1536, and one shared expert; microbatch 2 by sequence length 4096, accumulation 32. Dense and sparse paths use FP8; model and loss compilation, selective activation checkpointing (SAC), and MTP 1 are active. The recorded runtime metadata is Torch `2.15.0.dev20260822+cu130`, Python `3.12.3`, DeepGEMM `2.3.0+f093a4c`, and DeepEP `1.2.1+1b8f467`. These are metadata observations, not complete import hashes or proof that a donor build is compatible.

The active forward path is HybridEP `dispatch_with_permute` → DeepGEMM FP8 FC1 → fused SwiGLU, router-probability multiplication, and FP8 quantization → DeepGEMM FP8 FC2 → HybridEP `combine_with_unpermute`. The grouped-expert call site shows the two GEMMs and the intervening probability-weighted SwiGLU ([FC1 through FC2](../../gift/torchtitan/models/common/moe/experts/gmm.py#L278)); HybridEP launches dispatch and combine through opaque buffer calls ([dispatch](../../gift/torchtitan/distributed/deepep/hybridep.py#L322), [combine](../../gift/torchtitan/distributed/deepep/hybridep.py#L512)).

The established tensor contract is E4M3 activations with FP32 scales shaped `[M, K/128]`, E4M3 expert weights with FP32 scales shaped `[E, N/128, K/128]`, and BF16 GEMM outputs. Preserve the existing scale arithmetic, accumulation precision, and rounding/cast points; using the same FP8 dtype does not establish bitwise parity when the accumulation tiling or order changes. Router probability is multiplied into the SwiGLU result before its intermediate FP8 quantization, and its gradient must remain connected. Backward includes M-grouped dgrad and row-to-column requantization followed by K-grouped wgrad. These details are visible in the [DeepGEMM wrapper](../../gift/torchtitan/ops/float8/deep_gemm_handle.py#L129), [grouped GEMM backward](../../gift/torchtitan/ops/float8/grouped_gemm.py#L138), and [expert path](../../gift/torchtitan/models/common/moe/experts/gmm.py#L289).

The current wrapper passes tensors, scales, weights, and row/group metadata into DeepGEMM; it exposes no readiness counter, wait flag, or partial-output publication mechanism ([custom-op boundary](../../gift/torchtitan/ops/float8/grouped_gemm.py#L124), [DeepGEMM handle](../../gift/torchtitan/ops/float8/deep_gemm_handle.py#L129)). HybridEP inserts a dependency on the whole dispatch before compute-stream consumption and treats its implementation handle as opaque. Combine also immediately joins communication to the compute stream. These are GPU stream dependencies, not a claim that the host waits for every kernel to finish. A fused scheduler cannot safely read an in-flight partial tensor through this unchanged interface.

| FC2 GEMM | 29.791 ms; 39 kernels | dgrad 14.210 ms; wgrad 22.222 ms |
| Combine / gradient collection | 65.846 ms; 39 calls | 41.624 ms; 21 calls |
| **Counted kernel-time sum** | **158.714 ms** | **167.347 ms** |

Each backward GEMM variant has 21 kernels. Across both passes, combine totals 107.470 ms and dispatch 50.156 ms. EP plus actual expert GEMMs totals 326.061 ms, or 25.20% of the elapsed window. These sums exclude intervening work and are not a removable-latency budget. Not all MoE helper kernels are included, and EP kernels can include peer waiting/spinning, permutation, or device synchronization rather than only communication transfer. The trace operators `dispatch_bwd` and `combine_bwd` respectively scatter output gradients to experts and collect input/probability gradients back to source tokens.

The compiled V2 backward trace already prioritizes FC2 dgrad, then FC1 dgrad, then combine-backward's collect, before the wgrads. Python lexical order is not runtime order, so source reordering alone is not a new optimization. SAC also matters: 15 of 39 forward/recompute episodes have FC1 cached, so it is incorrect to assume every dispatch can overlap FC1. Current SAC policy independently saves expert up-projection and communication results ([policy setup](../../gift/torchtitan/distributed/activation_checkpoint.py#L85), [expert-up choice](../../gift/torchtitan/distributed/activation_checkpoint.py#L196)); a fused opaque op must preserve the active save/recompute choices.

## Conditional opportunity arithmetic

The following scenarios assume every stated millisecond of the measured 157.626586 ms EP-kernel sum is hidden and shortens the same 1293.712761 ms elapsed window, with all other work unchanged. Latency reduction is `saved / T`; throughput change is `T / (T - saved) - 1`.

| Assumed EP time hidden | Saved time | Conditional elapsed-window reduction | Conditional throughput change |
| ---: | ---: | ---: | ---: |
| 25% | 39.407 ms | 3.046% | +3.142% |
| 50% | 78.813 ms | 6.092% | +6.487% |
| 75% | 118.220 ms | 9.138% | +10.057% |
| 100% | 157.627 ms | 12.184% | +13.875% |

The 100% row is an ideal fixed-work ceiling, not an expected gain. A narrower model that allows only the two forward pairings—dispatch with FC1 and FC2 with combine—gives `SUM_i[min(dispatch_i, FC1_i) + min(FC2_i, combine_i)] = 49.371700 ms`, or +3.97% conditional window throughput. That result bounds only that restricted pairing model; it is not a general bound on a fused backend that can change helper and GEMM scheduling. The capture's 42.899 ms of all-device idle (3.32% of its elapsed span) is likewise not a bound on algorithmic savings. None of these values is a measured candidate gain, and no after-GFSDP denominator exists for this work.

## Pinned donor evidence and fit

### Flux / COMET

Flux and COMET are the same implementation lineage, not two independent backend candidates. The pinned Flux revision is [`bytedance/flux@19831ca2d820e3e782ed1d15d8b52d0898b78b26`](https://github.com/bytedance/flux/tree/19831ca2d820e3e782ed1d15d8b52d0898b78b26). Its MoE AG-scatter implementation is custom C++/CUDA using CUTLASS and CuTe, with a grouped scheduler and cooperative GEMM kernels ([AG-scatter kernel](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/moe_ag_scatter/gemm_grouped_v3_ag_scatter.hpp#L63-L160)). This is evidence for a fused communication/GEMM design, not for plugging its public operator into the current DeepGEMM path.

The public AG-scatter operator exposes only an FP32 output scale per local expert, not activation or weight block scales ([operator arguments](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/moe_ag_scatter/ths_op/gemm_grouped_v3_ag_scatter.cc#L259-L264)); `ptr_alpha` is applied in the post-K epilogue ([epilogue](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/moe_ag_scatter/gemm_grouped_v3_ag_scatter.hpp#L304-L310)). Gather-RS instead accepts an input scalar and one weight scale per expert ([arguments](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/moe_gather_rs/ths_op/gemm_grouped_v3_gather_rs.cc#L343-L350), [device path](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/moe_gather_rs/topk_gather_rs.cu#L404-L408)). Its generated FP8 gather-RS specializations cover top-k 4, 5, and 6, not this workload's top-k 8 ([generator](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/src/generator/gen_moe_gather_rs.cc#L115-L126)). Supporting the existing recipe requires block scales along K inside partial accumulation; changing only the argument shape cannot provide that arithmetic.

One Megatron integration calls the donor with `output_vec_scale=None`; probabilities are gathered but not applied in that example, which is not proof of the required weighted-combine or full backward contract ([integration example](https://github.com/ZSL98/Megatron-LM/blob/91401c920b5b15c2aa08fdc9fb2630aa52510df7/tests/unit_tests/transformer/moe/test_moe.py#L472)). The pinned README's tested wheel matrix uses Torch 2.4/2.5/2.6, CUDA 12.4, NVSHMEM 3.2.5/3.3.9, and CUTLASS 4; compatibility with the recorded local build is unverified. This is not a reason to downgrade the production stack.

COMET v3 reports Hopper measurements on 8 H800s with 80 GB and NVLink, CUDA 12.3, NVSHMEM 2.11, and Torch 2.4 ([paper](https://arxiv.org/pdf/2502.19811v3)). Figure 10 uses EP8/TP1, global M from 2048 to 32768, D=4096, expert width 14336, and E=8/top-2 or E=32/top-4; reported baseline-relative averages range 1.28–2.37×. Figure 13 varies expert count and top-k and reports 1.16–1.83×. Figure 11 shows 86.5% communication hidden in one case. The baselines are Megatron CUTLASS, Transformer Engine, FasterMoE, and Tutel, not this HybridEP+DeepGEMM baseline. The paper's 1.71× abstract end-to-end claim does not establish full-training-step speedup for this workload.

Flux's official performance table reports, for 8 H800s and M=8192, K=N=8192, E=32/top-4, TP4/EP2, dispatch+GEMM at 4.069→1.335 ms (3.05×) and GEMM+combine at 6.672→1.685 ms (3.96×) ([MoE MLP table](https://github.com/bytedance/flux/blob/19831ca2d820e3e782ed1d15d8b52d0898b78b26/docs/performance.md#moe-mlp)). The baseline is a naive, unoptimized Torch implementation that also differs in indexing, fusion, and GEMM; dtype is not explicit, so the table is not evidence of BF16 or FP8 training parity. The local expert width is 1536, 9.33× narrower than 14336, with E=128/top-8 and a different token/rank distribution. H800 results do not directly predict an H100/H200 workload.

### FlashComm

The pinned [`ByteDance-Seed/Triton-distributed@7908e4ea9010bb2238f9f05b28c904fd4b71c60a`](https://github.com/ByteDance-Seed/Triton-distributed/tree/7908e4ea9010bb2238f9f05b28c904fd4b71c60a) FlashComm paths include persistent grouped GEMM kernels authored in CuTeDSL with TMA and WGMMA. The repository name does not mean these kernels are written in the Triton language; NVIDIA describes CuTeDSL as a Python-authored GPU-kernel programming interface ([CuTeDSL overview](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/overview.html)). The SM90 dispatch-GEMM class is [`CuTeDSLDispatchGroupGemmKernelSM90`](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/python/flash_comm/ep_overlap/kernels/cutedsl_dispatch_group_gemm_sm90.py#L29-L51); its matching public dtype contract is FP16/BF16 at [line 219](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/python/flash_comm/ep_overlap/kernels/cutedsl_dispatch_group_gemm_sm90.py#L219). Its FC2 class is a FlashComm implementation that pushes peer output directly in the epilogue, not a DeepGEMM backend ([GEMM-combine kernel](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/python/flash_comm/ep_overlap/kernels/cutedsl_group_gemm_combine_sm90.py#L29-L49)).

FlashComm's overlap path has readiness signals per expert, not a general tile queue; `dispatch_cutedsl` enables expert signals for intranode operation ([signal path](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/python/flash_comm/ep_overlap/ep_overlap_kernels.py#L572-L624)). The public standalone grouped-GEMM path compiles with `wait_signals=False`, so its readiness flag is dead-code eliminated ([grouped GEMM op](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/python/flash_comm/ep_overlap/_ops/group_gemm.py#L134-L142)). No ready-signal bridge to the current DeepGEMM API is established. FlashComm's existing MXFP8 format uses E8M0 scales per 32 values, not the local E4M3/FP32 block-128 recipe ([MXFP8 definition](https://github.com/ByteDance-Seed/Triton-distributed/blob/7908e4ea9010bb2238f9f05b28c904fd4b71c60a/FlashComm/include/flash_comm/quantization/mxfp8.h#L34-L55)). No Python autograd wrapper was found in the 48-file FlashComm subtree inspected; this limited search does not establish that no such wrapper exists elsewhere in the repository. Source protocols and supported dtypes are design evidence, not a drop-in FP8 training implementation. No published numeric Hopper latency table was found at this pin.

### DeepGEMM and other performance claims

The merged MegaMoE DeepGEMM pin [`5081f8513af57e61696de4f4f04b0e707ffb503e`](https://github.com/deepseek-ai/DeepGEMM/tree/5081f8513af57e61696de4f4f04b0e707ffb503e) is SM100 forward-only; at this revision, MegaMoE exports only `fp8_fp4_mega_moe`. Experimental SM90 pull requests exist ([#323](https://github.com/deepseek-ai/DeepGEMM/pull/323), [#473](https://github.com/deepseek-ai/DeepGEMM/pull/473)), but their H20/decode or FP8×MXFP4 conditions do not establish H100/H200 support for this blockscaled-FP8 training path. This is not a claim that no Hopper source exists; it is a fit and validation distinction. The 16 November follow-up below records relevant Hopper evidence at separate revisions and its limits.

MegaScale-MoE reports H800 352B training; its intra-operator ablation reduces iteration time by 7.1–12.9% across changes that include both MoE and attention, while its 1.88× full-system result also includes parallelism and system changes ([EuroSys 2026 paper](https://chaojin0310.github.io/files/papers/EuroSys26-MegaScale-MoE.pdf)). These are not isolated measurements of this overlap design. Taken together, the published results motivate investigating fused communication/GEMM scheduling but do not justify a local speedup estimate.

### 16 November 2026 follow-up: Hopper MegaMoE evidence

This update separates the still-SM100-only `5081f851` main-branch claim above from Hopper work available on other branches and forks. DeepGEMM PR [#383](https://github.com/deepseek-ai/DeepGEMM/pull/383) was merged into `nv_dev` as `572557e7ae9ad5331b81a1c250f141fba2c57962`, not into `main`. It adds SM90 all-FP8 MegaMoE with two launches: L1 performs dispatch, FC1, and SwiGLU; L2 performs FC2 and combine. It therefore offers a Hopper component baseline but no overlap between L1 and L2. The PR reports 3269 μs on H200 for Flash with 8192 tokens, against 4317.6 μs for DeepEP HT. That is an author-reported component forward comparison, not a full training measurement or evidence for this task's H100 setup.

The closest reviewed mechanism donor is still-open DeepGEMM [PR #440](https://github.com/deepseek-ai/DeepGEMM/pull/440), against `nv_dev`, from [`zkyue/DeepGEMM@8cf8180fe6f97eb65ee6638a14a21497cc1cb5e0`](https://github.com/zkyue/DeepGEMM/tree/8cf8180fe6f97eb65ee6638a14a21497cc1cb5e0). It implements all-FP8 in one persistent kernel, with a ring activation pool, tile-arrival flags, and lag-ordered L1/L2 work. Its author reports 8× H100 80 GB HBM3 GPUs (80 GB per GPU): at 2048 tokens per rank, 1.44–1.56×; at 8192, 1.33–1.43×, versus PR #383's summed split-kernel device times. At the 8192/rank row, reported device times are 3703→2578 μs for Flash and 8623→6503 μs for Pro. These are forward device-time comparisons on Flash D=4096, I=2048, E=256, top-6 and Pro D=7168, I=3072, E=384, top-6. The report also uses maximum-rank Kineto results, with cold-L2 bursts bracketed by three rounds. This comparison does not isolate overlap: PR #383 uses midscales per 64 with power-of-two scales, while the fused benchmark uses block-128 continuous FP32 scales. It is useful mechanism and measurement evidence, but the shapes differ from the local D=4096, I=1536, E=128, top-8 workload, and it provides no training, backward, SAC, or compile integration evidence.

PR #440's [SM90 API](https://github.com/zkyue/DeepGEMM/blob/8cf8180fe6f97eb65ee6638a14a21497cc1cb5e0/csrc/apis/sm90_fused_mega.hpp#L176) and [kernel](https://github.com/zkyue/DeepGEMM/blob/8cf8180fe6f97eb65ee6638a14a21497cc1cb5e0/deep_gemm/include/deep_gemm/impls/sm90_fp8_fused_mega_moe.cuh) use E4M3×E4M3, FP32 continuous scales, and block size 128 for activations and weights. Its API requires H and I divisible by 128, I≤4096, and E divisible by ranks; the local shape passes, and the default middle scale is 128. It requires transformed gate/up interleaving, symmetric buffers, and valid bounds on tokens from every rank: incorrect bounds can hang. Its kernel applies router probability after SwiGLU and before intermediate FP8 quantization and FC2, matching the local placement, but this does not establish exact rounding parity. Its scale is `max(amax, 1e-10)/448`, unlike PR #383's per-64 power-of-two recipe. At the 8192/rank bound, the report gives forward workspace figures of 3023→700 MiB for Flash and 5083→1113 MiB for Pro; these are not training peak-memory savings. The activation ring reuses intermediate storage, so backward would need an explicit retention or recomputation contract.

Pinned SGLang source shows a real SM90 framework integration, not a training proof: [`mega_moe_sm90.py@e0cf330b24e9d892e753a520ece201943694d1ff`](https://github.com/sgl-project/sglang/blob/e0cf330b24e9d892e753a520ece201943694d1ff/python/sglang/srt/layers/moe/mega_moe_sm90.py#L42-L86) stages BF16 input and routes it through symmetric buffers, then calls `fp8_mega_moe` with recipe 128, SwiGLU, and `fast_math=True`; its weight setup uses E4M3, block 128, and gate/up interleaving ([lines 97–149](https://github.com/sgl-project/sglang/blob/e0cf330b24e9d892e753a520ece201943694d1ff/python/sglang/srt/layers/moe/mega_moe_sm90.py#L97-L149)). Generic [`mega_moe.py`](https://github.com/sgl-project/sglang/blob/e0cf330b24e9d892e753a520ece201943694d1ff/python/sglang/srt/layers/moe/mega_moe.py) selects this SM90 path. This is a useful layout and buffer reference. The integration uses inference weights; optimizer-updated weights would require refreshing transformed persistent weights, and these files establish neither autograd nor SAC support. A separate [sgl-project/DeepGEMM PR #48](https://github.com/sgl-project/DeepGEMM/pull/48), merged at [commit `c28bb2964a9adc299d943ec4f00e39f66ae4cbed`](https://github.com/sgl-project/DeepGEMM/commit/c28bb2964a9adc299d943ec4f00e39f66ae4cbed), adds a decode heuristic that swaps AB up to 128 tokens; it is not evidence for training overlap or an SGLang runtime package pin.

The pinned [GC-MoE H100 report](https://github.com/Bruce-Lee-LY/gc-moe/blob/7902831ec4a6691b6268b308bcff5ec0cb15ec86/docs/h100_gc_moe.md) identifies its system as 8 L20Z H100s, 132 SM, NVLink, EP8; its D=5120, I=2304, E=384, top-6, M=1–256/rank setup reports a 1.113761× mean versus MegaMoE and 1.022447× at M=256. Its independent CuTe SM90 implementation of readiness signaling is not an unchanged DeepGEMM integration. It uses E4M3 activations with FP32 K=128 scales but MXFP4 E2M1 weights with K=32 scales, has no backward, and excludes staging and weight transforms. Reported timing uses graph capture, 10 warmup windows, 30 windows of 100 invocations, and maximum-rank medians. The separate H200 EP4 SELF scheduler A/B report is 1.024× and is not a DeepGEMM comparison. Paper [arXiv:2611.04222v1](https://arxiv.org/abs/2611.04222) describes H20/B300 at pin `9bdb81f`, not this H100 report.

Other evidence has narrower fit. [TeraMoE@162cf26f2c58452a90f7224aaf2714c1d79424be](https://github.com/PFCCLab/TeraMoE/tree/162cf26f2c58452a90f7224aaf2714c1d79424be) has actual DeepEP/DeepGEMM training code and a Paddle PyLayer FP8 wgrad, but its README specifies SM100 and EP32/64; there is no independent benchmark establishing it as a Hopper donor. vLLM issues [#42284](https://github.com/vllm-project/vllm/issues/42284) and [#65782](https://github.com/vllm-project/vllm/issues/65782) are RFCs, not confirmed merged Hopper training implementations. These pins refine the feasibility picture without changing selected option C, the rejection of shared-only or coarse-chunk overlap, or the absence of a local candidate benchmark. The current public whole-GEMM API cannot consume partial readiness, so integration still requires a custom forward/backward path for M-grouped dgrad, K-grouped wgrad, and router gradients; preservation of independent SAC choices for expert-up and communication; compiled fake/autograd integration; optimizer-aware transformed-weight refresh; correct symmetric-buffer lifetimes; and safe cross-rank token bounds. DeepGEMM is not a fundamental barrier; its current API integration is. No candidate benchmark or parity test has been run locally, and no speedup estimate follows from these external results.

## Integration boundary and evidence gates

Any prototype must preserve the block-scaled arithmetic in forward, dgrad, and wgrad; router probability placement and gradient; capacity/drop behavior, global expert IDs, and padding; ownership, synchronization, and symmetric-buffer lifetimes. The captured DeepGEMM kernels use a 116-SM configuration; any new allocation of GPU resources between communication and GEMM requires measurement under concurrent execution. The prototype must also preserve custom-op fake/autograd schemas, SAC's independent expert-up and communication choices, `torch.compile`, optimizer/master-weight and checkpoint semantics, and end-to-end training behavior. Donor forward examples do not establish backward correctness for this contract.

If implementation is separately authorized, evidence gates are: a forward/backward source prototype; baseline comparison of representative values and all affected gradients including router probabilities; compiled, SAC-enabled distributed EP execution; memory accounting; and paired unprofiled full-step measurements after startup, compilation, and warmup. These are future gates, not work performed or an implementation plan approved by this note. There are no local GPU/parity tests or candidate benchmarks. The research result is a selected backend direction with substantial integration cost and unproven performance value.
