# FIM

## Теория

При обучении MoE важной отличительной особенностью от dense моделей в данном случае является наличие MoE слоёв с неравномерным распределения токенов по экспертам. Учет неравномерного распределения токенов становится критичен при обучении в ep>1, так как потенциально появляется возможность отправить слишком много токенов на один ep rank и перегрузить девайс по памяти.

Для того чтобы избежать перегрузки девайсов применяется алгоритм дропа токенов, при достяжении заданной емкости ep rank-а лишние токены дропаются. Дроп токенов снижает качество обучения модели и служит только для критических моментов дисбаланса.

На данный момент ёмкость задаётся на уровне эксперта (количество токенов на 1 эксперта, которое не должно превышаться). При этом задавать ёмкость можно как абсолютным значением, так и относительным коэффициентом от среднего числа токенов на 1 эксперта.

Основной и рекомендуемый способ настройки - `dispatcher_balancing_strategy = "peak_capacity_factor"`. Он задаётся с помощью параметра `expert_capacity_factor`, а средняя ёмкость рассчитывается на основе максимальной длины последовательности и микробатча, планируемых на обучении. Такой режим лучше подходит для стабильной настройки конфигурации заранее и именно его стоит использовать по умолчанию.

Остальные режимы стоит рассматривать как дополнительные:
* `dispatcher_balancing_strategy = "capacity_factor"` - относительная ёмкость, задаётся с помощью параметра `expert_capacity_factor`. Средняя ёмкость рассчитывается на основе фактического количества токенов, пришедшего на экспертов на данном шаге. Подходит скорее для совместимости со старыми конфигами и точечных экспериментов;
* `dispatcher_balancing_strategy = "fixed_capacity"` - абсолютная ёмкость, задаётся с помощью параметра `expert_capacity_tokens`;

Дроп токенов в текущей реализации всегда происходит поэкспертно. При этом условие срабатывания дропа токенов может быть выставлено по группам с помощью параметра `drop_by_group_capacity`:
* `drop_by_group_capacity = False` (Дроп токенов срабатывает если перегружен хотя бы 1 эксперт, дроп реализуется поэкспертно);
* `drop_by_group_capacity = True` (Дроп токенов срабатывает если перегружен хотя бы 1 ep rank. Капасити ep rank-а рассчитывается как сумма капасити входящих в него экспертов. Дроп реализуется поэкспертно);

Рекомендуется выставлять капасити по экспертам максимальным входящим в ep rank, тк это потенциально позволяет достигать максимального перфа. Подробная методика по выставлению параметров описана в файле README.moe_perf.md

## Практика

Для использования token_drop-а необходимо заполнить в YAML-конфиге параметры `dispatcher_balancing_strategy` и в зависимости от выбранной стратегии дропа указать `expert_capacity_factor` или `expert_capacity_tokens`. Для нового конфига рекомендуется сразу использовать `peak_capacity_factor` и задавать `peak_capacity_microbatchsize`. Также при необходимости можно указать `drop_by_group_capacity = False`, по дефолту дроп происходит только при перегрузке ep_rank-а.

Рекомендуемая конфигурация по умолчанию для всех датасетов:
```yaml
model:
  ...
  config_overrides:
    ...
    dispatcher_balancing_strategy: "peak_capacity_factor"
    expert_capacity_factor: 2
    drop_by_group_capacity: true
    peak_capacity_microbatchsize: ${device_train_microbatch_size}
    ...
```

Альтернативно можно использовать legacy-режим `capacity_factor`, если нужно сохранить старое поведение:

```yaml
model:
  ...
  config_overrides:
    ...
    dispatcher_balancing_strategy: "capacity_factor"
    expert_capacity_factor: 2
    drop_by_group_capacity: true
    ...
```

Либо:

```yaml
model:
  ...
  config_overrides:
    ...
    dispatcher_balancing_strategy: "fixed_capacity"
    expert_capacity_tokens: 200_000 # очень грубая оценка приблизительного значения при ep=1
    drop_by_group_capacity: true
    ...
```
