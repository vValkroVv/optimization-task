# Dredd

## Установка и запуск

### Установка как пакет

```bash
pip install -e .

# Инициализировать submodule с логикой судейства
git submodule update --init --recursive contribs/arena-hard-auto
```

### Тесты (локальный quality gate)

```bash
# Установить тестовые зависимости
pip install -e ".[test]"

# Все unit + integration тесты (без e2e)
make test

# То же + отчёт покрытия и порог 60% по core-модулям
make test-cov
```

Дополнительно:

```bash
make test-unit
make test-integration
```

Маркер `e2e` зарезервирован для тестов с внешними сервисами и не запускается в дефолтных командах. Проект поддерживает высокий стандарт качества: общее покрытие тестами ключевых модулей (`dredd.py`, `src/utils/`, `src/models.py`) поддерживается на уровне выше 70-80%.

### Запуск

#### Использование дефолтного конфига

```bash
./dredd.py
# или
dredd
```

#### Использование кастомного конфига

```bash
python ./dredd.py --config configs/arena_hard_example.yaml
```

#### Использование дефолтного конфига + editable конфиг

```bash
python ./dredd.py --editable configs/editable.yaml
```

#### Использование кастомного конфига + editable конфиг

```bash
python ./dredd.py --config configs/arena_hard_example.yaml --editable configs/editable.yaml
```

#### Переопределение параметров через CLI

```bash
python ./dredd.py experiment.overwrite_generations=true
python ./dredd.py model.name="my-model" model.path="data/model_data/my-model"
python ./dredd.py baseline.name="gpt-4-0314"
python ./dredd.py baseline.max_tokens=8096
```

#### Запуск отдельных фаз

```bash
# Только генерация
python ./dredd.py --phase generation

# Только судейство (при отсутствии генераций они будут созданы автоматически)
python ./dredd.py --phase judgement

# Полный пайплайн (по умолчанию)
python ./dredd.py --phase all
```

#### Детальные логи (verbosity)

```bash
# Включить DEBUG-логи
python ./dredd.py -v

# Явно задать уровень логов
python ./dredd.py --log-level DEBUG

# Для судейства: печатать traceback и падать при любой ошибке оценки
python ./dredd.py judge.verbose_errors=true judge.fail_on_error=true
```

### Конфигурация и иерархия параметров



Dredd использует многоуровневую систему конфигурации на базе OmegaConf. Параметры объединяются в следующем порядке (каждый последующий уровень перезаписывает предыдущие):



1.  **Дефолтный конфиг** (`configs/default.yaml`): Базовые настройки проекта.

2.  **Editable конфиг** (передается через `--editable`): Файл для быстрых правок параметров без изменения основного файла.

3.  **Командная строка (CLI)**: Любые параметры, переданные как `key=value` (например, `model.temperature=0.5`).

4.  **Специфичные настройки датасета**: Если внутри блока `datasets` для конкретного датасета указаны свои блоки `model`, `judge`, `baseline` или `experiment`, они **перезаписывают** общие (глобальные) настройки только для этого конкретного замера.


### Параметры конфигурации

1. **api_type**:
- openai (Для обращения к ручке base_url/chat/completions)
- trt (Для обращения к ручке base_url/chat)
- ift (Для обращения на ифт, требует установленных переменных среды GIGACHAT_IFT_CLIENT_ID и GIGACHAT_IFT_CLIENT_SECRET. Если определить их в .env в корне проекта, они подгрузятся)


#### Пример логики слияния:

Если в глобальном конфиге `judge.temperature` равен `0.0`, но в списке датасетов указано:

```yaml

datasets:

  - name: "arena-hard-v2.0"

    judge:

      temperature: 0.5

```

То при замере `arena-hard-v2.0` будет использована температура `0.5`, в то время как для остальных датасетов она останется `0.0`.



Для просмотра всех доступных параметров для перезаписи используйте:

```bash

./dredd.py --help

```

### Итоговый (merged) конфиг

После слияния всех уровней Dredd автоматически сохраняет итоговый конфиг на диск — в файл, путь к которому задаётся параметром `merged_config_path` (по умолчанию `configs/merged_configs/merged_config.yaml` внутри репозитория).

Директория создаётся автоматически при первом запуске.

**При повторном запуске файл перезаписывается** — версионирование не ведётся, всегда хранится только последний вариант.

Это позволяет после запуска точно видеть, с какими итоговыми параметрами он был выполнен, включая все CLI-оверрайды и dataset-специфичные настройки.

Чтобы изменить путь сохранения:

```bash
./dredd.py merged_config_path=/abs/path/to/my_run.yaml
```



## Логика работы: Генерация и Судейство



Этот раздел предназначен для пользователей, которые хотят понять, куда сохраняются данные, и разработчиков, желающих доработать логику.



### 1. Структура директорий (Артефакты)



Все результаты работы Dredd сохраняются в структурированном виде внутри папки, указанной в `model.path` (по умолчанию `test_model_folder`):



```text

test_model_folder/

└── artifacts/

    └── arenas/

        └── <dataset_name>/ (например, arena-hard-v2.0)

            ├── generations/

            │   ├── default/           # Если генерации были импортированы или найдены по умолчанию

            │   └── <TIMESTAMP>/       # Уникальная папка для каждого нового запуска генерации

            │       ├── config.yaml    # Параметры, с которыми запускалась генерация (temp, tokens...)

            │       └── generation.jsonl

            └── judgments/

                └── <baseline_model_name>/

                    └── judgment.jsonl # Результаты судейства

```



### 2. Логика Генерации (Phase 1)

#### Откуда берутся генерации

Поведение зависит от того, задан ли в конфиге `model.path`:

- **`model.path` задан** — Dredd считает эту директорию "своей". Он ищет генерации там, создаёт новые run-директории там же и может дописывать незавершённые генерации.

- **`model.path` не задан** — Dredd ищет генерации внутри себя, в директории `data/model_data/<model_name>/`. Эти данные поставляются вместе с проектом и считаются **неизменяемыми**: Dredd никогда не пишет в них, только читает.

#### Приоритет поиска и роль `default/`

При поиске существующих генераций применяется следующий порядок:

1. **`default/`** — если существует папка `default/generation.jsonl`, она используется **всегда**, независимо от текущих параметров генерации. Папка `default` считается **неизменяемой**: Dredd никогда не дописывает и не перезаписывает её содержимое, даже если генерации неполные. То же правило применяется и при судействе — `default` имеет наивысший приоритет.

2. **Matching по конфигу** — если `default` отсутствует, Dredd ищет run-директорию, где `config.yaml` **точно совпадает** с текущими параметрами генерации (температура, max_tokens и т.д.). Если такой run найден и он неполный — Dredd его дополнит.

3. **Новый run** — если подходящая директория не найдена или `overwrite_generations: true`, создаётся новая директория с текущим временем (TIMESTAMP). В ней сохраняется `config.yaml` с параметрами текущей генерации для последующего matching.

#### Смарт-логика и отказоустойчивость

Перед началом генерации Dredd проверяет, нужно ли это делать:

1.  **Поиск существующих результатов:**

    Если в конфиге `experiment.overwrite_generations: false` (по умолчанию), скрипт сканирует папку `generations/`.

    *   Он читает `config.yaml` в каждой подпапке.

    *   Если находит папку, где параметры генерации (температура, топ-к и т.д.) **совпадают** с текущими настройками, он переиспользует этот файл.

    *   Если файл существует, но не полон (например, генерация прервалась), Dredd просто **допишет** недостающие ответы в конец файла.

2.  **Создание нового прогона:**

    Если подходящая папка не найдена или `overwrite_generations: true`, создается новая директория с текущим временем (TIMESTAMP). Изменение любого параметра (например, температуры) автоматически приводит к созданию новой папки, чтобы результаты разных экспериментов не перемешивались.

3.  **Возобновление (Resume):**

    Dredd автоматически пропускает вопросы, ID которых уже есть в целевом файле `generation.jsonl`. Чтобы продолжить прерванную генерацию, просто перезапустите скрипт с тем же конфигом и `overwrite_generations: false`.

4.  **Устойчивость к данным (Data Robustness):**
    Dredd корректно обрабатывает "грязные" входные файлы: пустые строки, лишние пробелы и некорректные JSON-записи в логах генерации будут проигнорированы, а не вызовут падение программы.



### 3. Логика Судейства (Phase 2)



Dredd выступает как **оркестратор** для внешней логики оценки (в данном случае `arena-hard-auto`):



1.  **Подготовка:** Скрипт находит файлы ответов для вашей модели (Candidate) и модели сравнения (Baseline).

2.  **Интеграция:** Используется прямой импорт логики `arena-hard-auto` из submodule-папки `contribs/`.

3.  **Динамическая конфигурация:** Dredd "на лету" подменяет настройки бейзлайна (Monkey-patching), чтобы вы могли сравниваться с любой моделью (например, GPT-4, Claude), даже если она не прописана в исходном коде бенчмарка.

4.  **Pairwise Evaluation:** Каждый вопрос оценивается дважды (поменяв модели местами), чтобы исключить позиционную предвзятость (Position Bias).

5.  **Оптимизация: Автоматические ничьи (Automated Ties):**
    Если ответы Candidate и Baseline на конкретный вопрос полностью идентичны (после нормализации текста), Dredd не отправляет запрос судье. Вместо этого он автоматически записывает вердикт `[[A=B]]` (ничья) и выводит предупреждение в лог. Это позволяет:
    *   Экономить время и деньги на API-запросах.
    *   Обеспечивать 100% точность оценки для идентичных ответов.
    *   Сохранять полноту статистики: такие вопросы учитываются в финальном Summary и влияют на итоговый скор (score 50.0).

6.  **Умная классификация:** Dredd умеет извлекать результаты не только из структурированных полей `score`, но и из сырого текста судейства, понимая операторы сравнения (например, `A<B` как победу Baseline).



**Примечание для разработчиков:**

В текущей реализации судейство использует `ThreadPoolExecutor` для параллельных запросов к API судьи. Убедитесь, что ваш API провайдер выдерживает заданный `parallel_api_calls`. При возникновении ошибок API (RuntimeError) Dredd не прерывает всё судейство, а логирует ошибку для конкретного вопроса и продолжает работу, чтобы максимально сохранить прогресс.


### Экспорт данных для парных доверительных интервалов

После судейства PAM может запустить в окружении DREDD:

```bash
python export_ci.py /path/to/pam/metrics/dredd
```

Экспорт читает `dredd_merged_config.yaml` и `arenas/*/judgments/*/judgment.jsonl`.
Для полного набора вопросов с валидными вердиктами он записывает
`ci_quality.json` рядом с результатами судейства: оценку каждого вопроса
в диапазоне 0–1 и идентификатор методики. Порядок игр и повторные записи
обрабатываются через существующий `compute_judgment_summary`.
Неполные результаты не экспортируются; старый файл CI удаляется перед пересчётом.
Сам доверительный интервал вычисляет Job Dispatcher. Обычный запуск DREDD
и формат сводных метрик не меняются.
