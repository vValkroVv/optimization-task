# Стенд

Файлы для воспроизведения измерительного запуска llm-foundry с сэмплером. Скрипты запускаются из корня репозитория
(`python -m stand.<скрипт>` или `python stand/<скрипт>.py` с `PYTHONPATH=.`).

## Запуск обучения

- `l8-allmetrics-stand.yaml` — конфиг на 300 шагов: все мониторы на каждом шаге, autometrics, eval и чекпоинты убраны, коллбэк `metric_sampler` первым в списке.
- `l8-allmetrics-v2.yaml` — то же на 120 шагов для проверки Parquet-версии коллбэка.
- `submit_stand.py <config> [n_workers] [exp_name] --llmf-root <чекаут llm-foundry> --stand-root <каталог> --user-login <логин> --region <регион>` — сабмит через `TrainJobLLMF` из выбранного чекаута llm-foundry и его contrib. Конфиг берётся из `<stand-root>/configs`, логи пишутся в `<stand-root>/jobs_logs` и `<stand-root>/slurm_logs`. Значений по умолчанию для каталогов, логина и региона нет. Фрагмент конфига — `metric-sampler-production.yaml`.
- `submit_shm_probe.py` — те же аргументы и `--base-image <образ>`: ставит в очередь `shm_node_probe.py` из `<stand-root>` на одном узле.
- `submit_kernel_check.py [скрипт стенда [аргументы]]` — те же аргументы, `--base-image <образ>` и `--repo-root <чекаут этого репозитория, видимый заданию>`: ставит в очередь проверку на узле с GPU (по умолчанию `check_activation_kernel.py`).
- `llmf_metric_sampler_callback.py` — совместимый импорт callback из выбранного llm-foundry. Не копируйте этот файл поверх `llmfoundry/callbacks/metric_sampler.py`: реализация находится в самом llm-foundry.
- `llmf_metric_sampler_ab.py` — стендовая обёртка: блоки шагов по очереди проходят шесть режимов захвата. `off` — захвата нет, все наблюдатели отключены; `base` — снимки dispatcher, скаляры потерь, host-скаляры, тайминги GPU, память и норма клиппинга; `tokens` — `base` плюс исходные назначения роутера и статистики потерь токенов, потоков и экспертов; `full` — `tokens` плюс наблюдатель градиентов до редукции; `acts` — `full` плюс статистики активаций, то есть обычный сбор; `detailed` — `acts` с тяжёлыми гистограммами потерь на каждом шаге. Статистики активаций собираются для каждого ранга и микробатча в обоих режимах с активациями; наблюдатели активаций и dispatcher включаются перед каждым forward и отключаются перед backward. Частичные режимы намеренно имеют пропущенные обязательные слоты; для проверки полноты используйте обычный callback `metric_sampler`. Времена начала шагов пишутся в каждом блоке, так что стоимость режимов измеряется внутри одного запуска на одном узле; для боевых конфигов обёртка не предназначена.
- `ab_analyze.py <каталог запуска> <размер блока>` — сводка A/B по `ab_batch_starts/rank*.tsv` (шаг, режим, время начала) первых двух рангов: среднее медиан длительности шага по блокам для `off` и для остальных режимов с разностью, процентом и стандартной ошибкой; первые 100 шагов не учитываются.
- `build_activation_ext.py [build_root]` — заранее собирает CUDA-расширение статистик активаций в каталог с хешем исходников, из которого читает `activation_ext.load()`. Запускать на узле с GPU в образе обучения при каждом изменении `csrc/`.

Для A/B оставьте модель, входные данные, batch size и остальные мониторы одинаковыми.
Уберите прогрев и переходные шаги; сравнивайте полное время шага `off` и `acts`, отдельно
`detailed`. `ab_batch_starts/rank*.tsv` содержит времена начала шагов всех режимов.
Обёртка измеряет добавочную стоимость raw callback: отдельный logger и включённые
мониторы продолжают работать в `off`. Результаты старых замеров не характеризуют новый
сбор каждой карты/микробатча. До повторного замера overhead не подтверждён.

## Проверки на узле с GPU

Каждая проверка сравнивает ядра и расширения с эталоном и завершается ненулевым кодом при расхождении.

- `check_activation_kernel.py [--correctness-only | --timing-only] [--baseline-ref <коммит>] [--breakdown]` — сверяет с эталоном CUDA-расширение и Triton-ядро статистик активаций (гистограммы на обычных и детальных шагах, суммы с границей ошибки округления, моменты степеней, сырые счётчики bf16/fp16, точные квантили, нормы строк, нормы весов). С `--baseline-ref` собирает расширение этого коммита рядом с текущим, побитно сравнивает все целочисленные слова, которые они записывают, и печатает таблицу времени GPU каждого вызова (повтор CUDA graph) для форм активаций L8 и более широких; `--timing-only` печатает только таблицу, `--breakdown` — ядра каждого вызова. Запуск на узле: `python submit_kernel_check.py check_activation_kernel.py <аргументы>`.
- `check_token_loss_kernel.py` — сверяет Triton-путь `TokenLossStats` (запуск на `observe_routing`, на `observe_loss` и на каждый маршрутизируемый сегмент) с torch-эталоном на тех же тензорах и том же `Layout`/`RankRecorder`: формы из `_SHAPES`, одна и две головы MTP, 44 потока, обычный и детальный шаг, два разных микробатча (последний меньше). Счётчики (гистограммы, `*_count`, `*_samples`) сравниваются точно, суммы (`*_sum`, `*_sumsq`) — с относительным допуском 1e-5, потому что порядок атомарного сложения отличается, `loss/token_max` — точно. Слова, записанные запуском через `triton_launch.launch`, сравниваются со словами тех же наблюдений через JIT-вызов. Затем печатает таблицу времени одного микробатча для torch-эталона и Triton-пути (диагностика, не накладные расходы обучения).
- `check_attention_kernel.py [--correctness-only]` — сверяет ядра статистик внимания `AttentionStats` (CUDA-тензоры) с torch-эталоном на копиях тензоров на CPU, слово за словом: счётчики строк точно, остальные поля с точностью до округления float32 при другом порядке редукции, NaN и бесконечности там, где они есть в эталоне. Покрывает нечётные и боевые размерности головы, bf16 и float32, плотные и плоские строки, тензоры со страйдами, нефинитные значения, повторные наблюдения одного слота и новый шаг; проверяет детерминизм (одинаковые биты в каждом запуске), все конфигурации перебора (tile rows, warps, target programs) и совпадение слов при прямом и JIT-запуске. Вторая половина измеряет время GPU одного наблюдения относительно прочитанных байтов, время выдачи вызова на CPU (прямой запуск и JIT) и перебирает конфигурации ядер на боевых формах.
- `check_quantiles.py --output <json> [--repeats N]` — строгие проверки точных квантилей (граничные случаи, маски, ничьи, знаковые нули, субнормальные и нефинитные значения, захват в recorder) и измерение стоимости вычисления квантилей полной популяции; результат пишется в JSON.
- `check_expert_balance.py --output <json>` — строгие проверки операндов балансировки экспертов в recorder: знаменатель по валидным токенам, объединение повторных вызовов, структурные нули владения, float64-суммы, локальный bias, нефинитные значения, бинарные маски; побитовое сравнение накопления роутера, квантилей энтропии и нативных вызовов `RouterBalanceCalls` и `ExpertActivationCalls` с эталонными путями.
- `shm_node_probe.py` — проба допущений узловой агрегации, запускается через torchrun на одном узле с 8 GPU (или через `submit_shm_probe.py`). Для каждого ранга проверяет, что сегмент `/dev/shm` регистрируется через `cudaHostRegister`, что копия в него действительно асинхронна, и замеряет захват телеметрии 61 MoE-слоя в один плоский буфер плюс одну копию device-to-host; ранг 0 узла проверяет, что видит сегменты всех рангов и что записанный DMA номер шага виден в каждом payload.

## Бенчмарки и проверки без GPU

- `bench_aggregator.py [--steps N] [--window-steps N] [--configs L8 L16 L61 L61+act] [--profile]` — синтетический бенчмарк пути агрегации узла: строит `Layout`, `ShmRing` и `RankRecorder`, прогоняет шаги и раздельно замеряет `RankRecorder.step_end`, проход декодирования и слияния `NodeAggregator` и запись окна для нескольких масштабов. Укороченный layout не содержит потерь токенов и экспертов, поэтому память полного задания не оценивается.
- `bench_collector_encoding.py --raw-root <raw-root> [--windows N]` — на узле коллектора с `PYTHONPATH` коллектора (chdb, pyarrow, репозиторий): сравнивает кодировки Parquet для загрузки коллектором на реальных окнах узлов (`<raw-root>/_collected` тоже подходит). Для каждого кандидата (текущий писатель chdb с вариантами настроек и pyarrow с вариантами кодировок) печатает байты, CPU и время кодирования, ядра на поток файлов узлов, CPU и время декодирования chdb в структуру приёма и проверку `count + sum(cityHash64(*))` против окон узлов. С `--s3-endpoint --s3-bucket --s3-prefix --s3-remote-section` дополнительно загружает объекты в `<prefix>/bench-<id>/` и замеряет три способа проверки числа строк; без них ничего не загружает.
- `check_byte_stream_split_read.py --out <dir> [--clickhouse-dir <путь каталога для сервера>]` — пишет pyarrow одни и те же строки (`Array(UInt32)` со значениями выше 2^31, `Array(Float32)` с NaN, бесконечностями и пустыми массивами) обычной и byte_stream_split кодировкой и `check.sql`, который читает оба файла обоими парсерами Parquet сервера и сравнивает число строк, хеш строк и суммы; запуск: `clickhouse-local --multiquery < <dir>/check.sql` или `clickhouse-client` с каталогом внутри `user_files_path`. Везде должно быть `identical: 1`.
- `check_dashboards.py <каталог дашбордов> <exp> <run> <layer> --password-file <файл> [--step N] [--rank N] [--microbatch N] [--detail-rank N] [--require-data]` — на хосте Grafana прогоняет запросы всех панелей и переменных дашбордов через `/api/ds/query`, подставляя значения переменных; пароль администратора Grafana читается из файла. Ненулевой код возврата, если запрос не удался (с `--require-data` — и если он вернул ноль строк).

## Проверка данных запуска

- `validate_window.py <окно>` — проверяет окно узла, записанное агрегатором, по инвариантам конфига стенда: 8 рангов на узле, 2 микробатча по 12 последовательностей × 4096 токенов, top-8 маршрутизация.
- `validate_distributions.py <run_dir> <top_k> <tokens_per_microbatch>`, где `run_dir` — `<raw root>/<exp>/<run>`; окна, уже перенесённые в `<raw root>/_collected/<exp>/<run>`, читаются тоже; нужны pyarrow и пакет в `PYTHONPATH`. Для каждого шага и узла, где есть статистики токенов, проверяет: (1) токены гистограммы равны числу токенов потока; (2) на основных слоях число токенов эксперта равно `top_k` × числу токенов потока, а сумма потерь экспертов / `top_k` равна сумме потерь потока; (3) на слоях MTP число токенов эксперта равно `top_k` × токены гистограммы MTP; (4) взвешенное среднее потока согласуется со средним `loss/ce` по рангам и микробатчам; (5) среднее гистограммы отличается от точного не более чем на полбина; (6) на каждом шаге итоги гистограммы энтропии роутера, на детальных шагах — гистограмма экспертов и счётчики эксперт × поток; (7) активации: гистограмма RMS по токенам покрывает каждый токен, число элементов на токен целое и одинаковое для residual, attn_out и mlp_out, общий RMS лежит в диапазоне RMS по токенам, а на детальных шагах экспоненциальная гистограмма покрывает все конечные элементы и наибольший amax по карте ниже верхней границы верхнего непустого бина.

Узловой агрегатор пишет окна в `<output_dir>/attempt=<id>/node=<host>/w<a>-<b>/`, логгер — в `attempt=<id>/logged/w<a>-<b>/`. Коллектор из `metric_sampler.island` переносит их в S3.
